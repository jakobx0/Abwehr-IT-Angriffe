>[!abstract] Grundlagen Portscann:
>Es existieren verschiedene Scan-Typen, die je nach Aufbau der Pakete unterschiedliche Reaktionen auf Seiten von Betriebssystemen und Diensten auslösen. Das Antwortverhalten hängt von mehreren Faktoren ab, unter anderem von aktivierten Firewalls sowie IDS- oder IPS-Komponenten. Eine Auswahl relevanter Scan-Varianten ist in Tabelle 1 aufgeführt.
>
>```bash
>nmap -sT -n HOST/24 #für einfachen TCP Handshake-Scan des Netzwerkes
>```
>
>![[Pasted image 20260204214346.png]]
>
>Ein (Software-)Port stellt die Kommunikationsschnittstelle eines Dienstes oder einer Anwendung dar. Die Adressierung erfolgt über Port-Nummern im Bereich von 0 bis 65535 (2 Byte). Für jede auf OSI-Schicht 4 etablierte Verbindung existieren dabei immer ein Quell- und ein Zielport.
>
>![[Pasted image 20260204220121.png]]
>
>Im Laufe der Zeit haben sich für viele Dienste feste Standardports etabliert, die im Bereich 0 bis 1023 liegen und vom System reserviert werden. Dadurch wird eine eindeutige Zuordnung zwischen Port-Nummern und typischen Diensten ermöglicht. So verbirgt sich hinter Port 22 in der Regel ein SSH-Dienst, hinter Port 53 ein DNS-Service und hinter Port 80 ein Webserver (vgl. Tabelle 3). Die angebotenen Dienste sind oft eng mit bestimmten Netzwerkprotokollen verknüpft. Um jedoch herauszufinden, welche konkrete Anwendung einen Dienst bereitstellt, ist zusätzliche Analyse notwendig.
>
>![[Pasted image 20260204220434.png]]
>
>Welche Ports an einem System offen oder geschlossen sind, hängt davon ab, welche Dienste tatsächlich betrieben werden. Sind Portfilter wie Firewalls aktiv, kann eine Anfrage an einen nicht autorisierten Port verworfen werden, ohne dass eine Antwort generiert wird. Alternativ kann das System eine ICMP-Nachricht zurücksenden. Je nach eingesetzter Scan-Strategie entstehen dadurch Mischformen in der Interpretation, etwa wenn ein Port zwar nicht gefiltert wirkt, aber keine eindeutige Aussage darüber möglich ist, ob er offen oder geschlossen ist.

>```bash
>sudo nmap -sn -n 192.168.2.102/24 #ping scanns und ARP
>#`-sn` = **nur Hosts finden**
>```

>[!example] lokales Netz scannen:
>```bash
>sudo nmap -sS -n 192.168.2.0/24 #Scannt das gesamte 192.168.2.0/24: findet aktive Hosts (meist per ARP) und macht dann einen TCP SYN (Half-Open) Portscan über Nmaps Standard-Top-Ports (~1000), ohne DNS (-n)
>
>#`-sS` = **Hosts finden + TCP-Ports prüfen**.
>```

>[!example] Host Dicovery:
>**Idee:** Im LAN muss ein Sender zu einer Ziel-IP zuerst die **MAC-Adresse** kennen. Ist sie nicht im ARP-Cache, wird ein **ARP-Request als Broadcast** gesendet; **nur der Host mit der passenden IP** antwortet mit einem **ARP-Reply**, der seine MAC verrät. Damit lassen sich **aktive Hosts** im Subnetz erkennen.
>
>`arp.opcode == 1` -> Host request
>`arp.opcode == 2` -> Host reply (für "aktive Hosts")
>
>**Worauf achten:**
>- Request: „Who has X.X.X.X? Tell Y.Y.Y.Y“
>- Reply: „X.X.X.X is at aa:bb:cc:dd:ee:ff“

>[!question] 1.4.2 Offene vs. geschlossene vs. gefilterte Ports (z. B. 80 vs 81)  
>**Offen (open):**
>- Probe `SYN` → Antwort **`SYN/ACK`** (Handshake möglich)
>
>**Geschlossen (closed):**
>- Probe `SYN` → Antwort **`RST/ACK`** (Host erreichbar, aber kein Dienst lauscht)  
>
**Gefiltert (filtered):**
>- **Keine Antwort** (Drop) **oder** **ICMP Unreachable** (je nach Firewall/Filter)  
>
**Wireshark-Helferfilter:**
>- Nur SYN/ACK-Antworten: `tcp.flags.ack == 1 && tcp.flags.syn == 1`
>- Nur RST (typisch closed): `tcp.flags.reset == 1`
>
>>[!example] Nur offene Ports anzeigen  
>>**Ziel:** Nur die Pakete zeigen, die „Port ist offen“ signalisieren → **SYN/ACK**.
>>`tcp.flags.ack == 1 && tcp.flags.syn == 1 && tcp.analysis.retransmission`
